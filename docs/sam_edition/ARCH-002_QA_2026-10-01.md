## Structural verification

The QA build compiled with explicit static assertions for the compensated layout.

Verified:

- `sizeof(struct SamEditionSaveData) == 0xF0`
- `sizeof(struct SaveBlock1) == 0x3D68`
- `offsetof(SamEditionSaveData, coreMetadata) == 0x00`
- `offsetof(SamEditionSaveData, globalMechanicAux) == 0x10`
- `offsetof(SamEditionSaveData, greenName) == 0x50`
- `offsetof(SamEditionSaveData, rivalRocketAux) == 0x58`
- `offsetof(SamEditionSaveData, gymSatoshiPostgameAux) == 0x90`
- `offsetof(SamEditionSaveData, futureExpansion) == 0xC0`
- `offsetof(SaveBlock1, flags) == 0x0EE0`
- `offsetof(SaveBlock1, vars) == 0x1000`
- `offsetof(SaveBlock1, mysteryGift) == 0x3120`
- `offsetof(SaveBlock1, samEdition) == 0x352C`
- `offsetof(SaveBlock1, ramScript) == 0x361C`

Therefore the Sam Edition block occupies `0x352C-0x361B`, immediately followed by `ramScript` at `0x361C`, while the total SaveBlock1 size remains `0x3D68`.

## Save-path inspection

`SaveBlock1` is divided across the normal SaveBlock1 sectors by `sSaveSlotLayout`.

Normal save calls `SaveSerializedGame()` and writes the full save slot through the standard sector/checksum machinery.

Normal load uses `TryLoadSaveSlot()`, validates sector signatures/checksums, then calls `LoadSerializedGame()`.

`SamEditionSaveData` is therefore persisted as part of the ordinary SaveBlock1 byte stream; it has no independent serializer that could bypass standard checksum/load handling.
